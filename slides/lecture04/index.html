Part 1有监督学习算法

文本分类任务设定

为了把算法讲清楚，这一讲先固定成一个最简单的文本分类任务。

DATA
公开中文评论
酒店、电商、外卖评论都可以。
数据公开，课后也能复现。
TASK
负面 / 非负面二分类
输入一条评论，输出一个标签：
`negative` 或 `non_negative`。
GOAL
比较常见算法
朴素贝叶斯、逻辑回归、决策树，
看它们各自怎么做同一个任务。
评论 A：房间干净，前台也很热情，下次还会住。
评论 B：图片和实际不符，入住体验很差，不会再来。
评论 C：位置方便，但早餐普通，整体还能接受。
评论 D：退房三天还没退款，客服一直没人回，很生气。
Input
评论文本
一句中文评论
Model
算法处理
提取线索并判别
Output
分类标签
negative / non_negative

常见算法的基本直观比较

同一个分类任务，不同算法的“想法”并不一样。

ALGO 1
朴素贝叶斯：像数词
看哪些词更常出现在负面评论里，
哪些词更常出现在非负面评论里。
ALGO 2
逻辑回归：像打分卡
每个线索加一点分、减一点分，
最后合成一个总分。
ALGO 3
决策树：像连续提问
一步步问：有没有退款、有没有失联、
有没有强烈抱怨。
Naive Bayes
退款 + 异味 → 负面概率上升
干净 + 热情 → 非负面概率上升
核心直觉：先看词，再比较两边证据。
Logistic Regression
退款 +3 + 异味 +2
没人回 +2 → 总分 7
核心直觉：把多个线索加权后合成一个分数。
Decision Tree
有退款？ → 有失联？
是 / 是 → 负面
核心直觉：按条件一路分下去，像走流程图。
记忆时可以抓三个动作：看词频、做加权、走流程。

算法一：朴素贝叶斯的词频判别机制

它先把一句话拆成词，再看这些词更像常出现在负面，还是常出现在非负面。

“图片和实际不符，不会再来。”
负面词证据
不符
不会再来
退款
非负面词证据
干净
热情
还会来
判别结果
negative
如果这句话里出现的词，整体更像常见于差评， 模型就会把它往负面一侧推。
朴素贝叶斯不会先理解整句语义，它先看词：`不符`、`不会再来`、`差` 之类的词，在负面评论里是否更常见。

Part 1算法的适用条件与局限性

朴素贝叶斯的适用条件与局限性

它快、轻、好上手，但它也会忽略很多上下文信息。

优势

快：训练和预测都很轻，适合先跑第一版。
稳：当关键词信号很强时，表现常常不差。
省：对小样本和稀疏文本也比较友好。
vs

局限性

不看顺序：词和词之间的组合关系抓得比较弱。
假设很强：默认各个词的贡献彼此独立。
怕语境：“不差”“还行”这类细微表达不一定处理得好。

算法二：逻辑回归的加权判别机制

它不只是看词出现没有，而是把多种线索加权后合成一个分数。

“房间有异味，要求退款，客服一直没人回。”
异味
+2
退款
+3
没人回
+2
总分
7 分
分数越往右，越像 negative。 逻辑回归的直觉不是“哪个词最多”，而是“这些线索加起来有多危险”。
逻辑回归的直觉不是“哪个词最常见”，而是“哪些线索一起出现后，总体会把评论推向负面”。

逻辑回归作为基线模型的原因

做文本分类时，逻辑回归经常是一个很好的起点。

WHY 1
好解释
每个线索的方向和权重都比较直观，
容易向别人解释模型在看什么。
WHY 2
好扩展
既能吃词袋特征，
也能接更多结构化特征或 embedding。
WHY 3
好比较
很适合拿来做课程里的 baseline，
再和其他算法比较错误类型。

算法三：决策树的递归划分机制

它更像一个判断流程：每走一步，就把评论分到更细的一类。

有没有退款词？
有 / 没有
有没有客服失联？
有 / 没有
如果两者都有
很可能是负面
如果只有轻微抱怨
可能是非负面
决策树最擅长的， 是把“如果 A 又 B，就更像负面”这种组合条件直接写进判断过程。

决策树的优势与风险

它直观、像流程图，但也最容易把局部规律学得太死。

优势

直观：很像人工在脑中走的判断流程。
会抓交互：“退款 + 失联”这类组合条件表达得很自然。
好展示：课堂上容易把判断路径讲给学生看。
vs

风险

容易过拟合：树开得太深，就会把训练样本记得太细。
不够稳定：样本稍有变化，树结构可能就改很多。
要剪枝：否则很容易看起来很懂，实际泛化很差。

算法的综合比较

它们都能做文本分类，但各自擅长的地方并不一样。

解释性更强
对复杂关系的表达更强
朴素贝叶斯 快，轻，适合看强词信号。
逻辑回归 平衡，稳妥，适合做基线模型。
决策树 规则直观，但最容易过拟合。
算法 直觉 更适合 短板
朴素贝叶斯 看词证据 关键词很强、先跑快速基线时 不看词序，上下文能力弱
逻辑回归 做加权打分 文本分类 baseline、需要解释时 复杂交互要靠额外特征
决策树 走判断流程 规则型任务、组合条件很多时 容易过拟合，结构不稳定

Part 2提示词工程（Prompt Engineering）

少样本学习（Few-shot Learning）

对文本分类任务来说，最常见也最有效的输入提示方法之一，就是先给模型几个带标签的例子。

WHAT
先给示例
把几条已经标好标签的评论放进输入 prompt，让模型先看到任务长什么样。
WHY
再校边界
真正有用的 few-shot，不是最明显的正负例，而是最容易分歧的边界样本。
GOAL
最后再做泛化
模型不是在背答案，而是在从这些例子里学会这次分类任务的口径。

输入 Prompt 的六段骨架

现在更实用的写法，不是只写一句任务，而是把输入 prompt 拆成几个稳定的段落。

1
身份
你是谁，负责什么类型的文本判断。
2
任务
明确是分类、抽取、排序，还是生成解释。
3
标签定义
`negative` 和 `non_negative` 分别是什么意思。
4
边界规则
轻微抱怨、补偿后接受、混合情绪怎么算。
5
示例
优先放最容易分歧的 few-shot 边界样本。
6
当前输入
把这一次要分类的评论单独放在最后。

零样本 Prompt 示例

先不给例子，只把任务和规则写清楚，这就叫 zero-shot prompt。

你是中文评论分类助手。

任务：把评论标成 `negative`
或 `non_negative`。

规则：
1. 退款、异味、失联，判 `negative`。
2. 轻微不满但总体接受，判 `non_negative`。
3. 输出 JSON：
{"label": "...", "reason": "..."}
评论：
“位置方便，但早餐普通，整体还能接受。”
{
  "label": "non_negative",
  "reason": "有轻微抱怨，但总体仍可接受"
}

Few-shot 示例的边界校准作用

真正该补进 prompt 的，不是最明显的样本，而是最容易分歧的样本。

边界评论 标签 为什么值得放进 prompt
位置方便，但早餐普通，整体还能接受。 non_negative 提醒模型：轻微抱怨不自动等于负面。
外卖送到时已经凉了，不过客服马上补送了。 negative 提醒模型：即使有补救，也可能仍然是负面体验。
隔音一般，这个价位也就这样吧。 non_negative 提醒模型：模糊表达最容易误判，需要提前定规则。

Prompt 设计中的歧义表达问题

像“情绪不好”“体验一般”这种写法，模型和人都可能理解得不一样。

歧义表达

例子：“帮我判断哪些评论比较差。”
问题：“比较差”到底指强烈差评、轻微抱怨，还是需要人工复核？
结果：模型每次都可能抓不一样的边界。
vs

可执行表达

例子：“明确抱怨退款、异味、客服失联，标成 `negative`。”
补充：“轻微不满但总体接受，标成 `non_negative`。”
结果：同一个任务会更稳定，也更容易检查。

长上下文输入的组织原则

最新的主流做法都强调：把输入 prompt 分区，而且把静态规则放前面，把本次文本放后面。

前面放静态内容
角色、任务、标签定义
中间放规则与示例
边界规则、few-shot 样本
最后放当前输入
本次待分类的评论文本
写法上也要分区： 可以用 Markdown 标题、编号步骤，或 XML 标签把 <instructions>、<examples>、<input> 分开，这样模型更不容易把规则和样本混在一起。

复杂任务的 Prompt Chaining

当任务太复杂时，不要把所有动作塞进一个输入 prompt；拆成两到三步通常更稳。

STEP 1
先抽取关键信号
先让模型找出抱怨点、关键词、问题类型，不急着给最终标签。
STEP 2
再做标签判断
根据前一步抽取出的线索，再判断 `negative` 或 `non_negative`。
STEP 3
最后生成简短理由
只在最后补一句解释，避免模型一边判断一边把任务做散。
对分类、抽取、证据定位这类任务，这种“抽取 → 判断 → 解释”的链式提示，往往比一条 prompt 包打天下更稳定。

主流模型的输入提示偏好差异

现在市面上的共识越来越清楚，但不同平台对输入 prompt 的偏好并不完全一样。

OPENAI
清楚分角色，提示要直接
整体角色放在 system / developer，任务细节和示例放在 user；对推理模型，提示越清楚直接越好，不必反复要求“请一步一步思考”。
ANTHROPIC
强调 XML 标签和多样示例
官方文档反复强调用 XML 标签分开 instructions、examples、input；few-shot 最好放 3-5 个相关且多样的示例。
GEMINI
强调分区和格式示范
官方指南强调用 tags 或 Markdown 区分 instructions、context、task；few-shot 的一个重要作用，是先把目标格式教给模型。
